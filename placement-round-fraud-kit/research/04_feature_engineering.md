# Phase 5 — Feature Engineering

Generated by `src_research/04_feature_engineering.py` against `data/bank_transactions_data_2.csv`, sorted `AccountID` → `TransactionDate` → `TransactionID` (the same chronological sort used by the existing v1 pipeline, `src/fe_utils.py::fit_engineer`). Output: `artifacts_research/features_v2.csv` — 2,512 rows × 48 columns (2 ID columns + the 20 v1 features, reused unchanged, + 26 new Phase 5 columns). Diagnostics: `artifacts_research/phase5_diagnostics.json`.

Every feature below that touches "this account's history" or "who else shares this device/IP/merchant" is computed so only strictly prior rows are visible — never the current row, never a future one. The script asserts this by recomputing `TimeSinceLastTxn` independently and checking it matches `artifacts/features.csv` row-for-row before concatenating (**confirmed: MATCH**) — the two feature sets are safely aligned by position, not by an unverified assumption.

## 1. Feature Dictionary

| Feature | Formula | Business rationale | Leakage-safety note |
|---|---|---|---|
| `Velocity_1D_Count` | Count of this account's transactions in the trailing 1 day, **excluding** the current transaction (`groupby('AccountID').rolling('1D', closed='left').count()`) | Card-testing / rapid cash-out bursts | Time-window rolling with `closed='left'`; current row never included |
| `Velocity_7D_Count` | Same, trailing 7 days | Slower-burn burst detection | Same as above |
| `Expanding_MeanAmount` | Running mean of this account's `TransactionAmount`, prior rows only (`shift().expanding().mean()`) | This account's personal baseline | `shift()` removes the current row before the expanding window starts |
| `Expanding_MedianAmount` | Running median, prior rows only | Robust personal baseline (less outlier-sensitive than the mean) | Same |
| `Expanding_StdAmount` | Running std, prior rows only | Personal variability baseline, feeds the z-score below | Same; 0 or 1 prior observations → filled 0 (documented, not silent) |
| `Expanding_MinAmount` / `Expanding_MaxAmount` | Running min/max, prior rows only | Personal range envelope | Same |
| `Rolling3_MeanAmount` / `Rolling3_StdAmount` | Mean/std of the **last 3** prior transactions only (`shift().rolling(3)`) | Recent-behavior baseline that reacts faster than full-history expanding stats | `shift()` first, then a fixed window over already-shifted (prior-only) values |
| `Amount_to_Balance_Ratio` | `TransactionAmount / (AccountBalance + ε)` | Scale-relative signal: a $1,500 transaction means different things at a $200 vs. $15,000 balance (per Phase 2/4 finding) | Same-row, non-temporal — no leakage risk (both values known at transaction time) |
| `Amount_to_RollingMean_Ratio` | `TransactionAmount / (Expanding_MeanAmount + ε)` | How large is this transaction relative to what this account normally spends | Inherits leakage-safety from `Expanding_MeanAmount` |
| `Amount_minus_ExpandingMean` / `Amount_minus_ExpandingMedian` | `TransactionAmount − Expanding_Mean/MedianAmount` | Absolute deviation from personal baseline | Same |
| `Amount_ZScore_Account` | `(TransactionAmount − Expanding_MeanAmount) / (Expanding_StdAmount + ε)` | Standardized personal-deviation score — the single most direct "how unusual is this for *this* customer" feature | Same |
| `Hour_sin` / `Hour_cos` | `sin/cos(2π·hour/24)` from `TransactionDate` | Cyclical time-of-day encoding (pipeline completeness for real deployment) | Same-row, no leakage — **but see caveat below: near-zero variance in this dataset** |
| `DOW_sin` / `DOW_cos` | `sin/cos(2π·day_of_week/7)` | Cyclical day-of-week encoding | Same-row, no leakage — **same caveat** |
| `CustomerTxnCountSoFar` | `groupby('AccountID').cumcount()` (count of prior rows in the same group) | Customer tenure/activity-level proxy | Leakage-safe by construction — `cumcount()` at row *i* counts only rows before it in sorted order |
| `SpendCV_Account` | `Expanding_StdAmount / (Expanding_MeanAmount + ε)` | Coefficient of variation — spending *variability*, not just level; a normally-stable account suddenly varying widely is a signal independent of the amount itself | Same |
| `ElevatedLoginFlag` | `int(LoginAttempts >= 2)` | Turns the near-discrete `LoginAttempts` column (95.14% at exactly 1, per Phase 2/4) into the near-binary security flag the EDA explicitly recommended, instead of feeding a smooth continuous value into distance-based models | Same-row |
| `ATM_Credit_InteractionFlag` | `int(Channel=='ATM' and TransactionType=='Credit')` | Isolates the rare ATM+Credit combination (73/2,512 = 2.9%) flagged as statistically justified by the Phase 4 χ²=136.91 (p<10⁻²⁹) `Channel`×`TransactionType` association | Same-row |
| `DeviceSharedAccounts_Prior` | Count of **distinct other** `AccountID`s that transacted on this `DeviceID` at a strictly earlier `TransactionDate` | Mule-account / shared-infrastructure proxy (Phase 1 hypothesis #3) | Explicit prior-only accumulation per device (own account excluded); genuinely point-in-time safe, stricter than v1's `DeviceTxnCount` (see reconciliation, Section 3) |
| `IPSharedAccounts_Prior` | Same, keyed on `IP Address` | Same rationale | Same |
| `MerchantSharedAccounts_Prior` | Same, keyed on `MerchantID` | Weaker signal than device/IP — see caveat below | Same |
| `Location_Freq` | Global frequency (proportion) of this `Location` value | Frequency-encoding alternative to v1's `Location_enc` label encoding, compared in Phase 6 | Global, not per-timestamp — same convention already used by v1's `DeviceTxnCount`/`IPTxnCount`/`MerchantTxnCount` (documented Phase 6 limitation, not new here) |

Reused unchanged from v1 (`src/fe_utils.py`), not duplicated: `TransactionAmount`, `CustomerAge`, `TransactionDuration`, `LoginAttempts`, `AccountBalance`, `Amount_vs_TypeAvg`, `DeviceTxnCount`, `IPTxnCount`, `MerchantTxnCount`, `Amount_vs_AccountAvg`, `DeviceNoveltyFlag`, `LocationNoveltyFlag`, `TimeSinceLastTxn`, `Location_enc`, `TransactionType_Debit`, `Channel_Branch`, `Channel_Online`, `CustomerOccupation_{Engineer,Retired,Student}`.

## 2. Findings, With Real Numbers

### 2.1 Velocity — mostly zero, exactly as the sparse per-account history predicts

`Velocity_1D_Count`: **2,462/2,512 rows (98.0%) are 0**, 48 rows are 1, 2 rows are 2. `Velocity_7D_Count`: **2,289/2,512 (91.1%) are 0**, 209 rows are 1, 14 rows are 2. This is the honest consequence of 495 accounts averaging 5.08 transactions spread across a 364-day span (Phase 2) — most accounts simply don't have two transactions close enough in time to produce a nonzero trailing count. The feature is still built because a real deployment with a genuine continuous transaction stream would see meaningfully more nonzero mass here; on *this specific dataset* it functions less as a graded velocity signal and more as a rare, high-precision flag — the 50 rows with `Velocity_1D_Count ≥ 1` and 223 rows with `Velocity_7D_Count ≥ 1` are a small, distinctive population worth inspecting directly rather than trusting as a smooth numeric input.

### 2.2 Ratio/deviation features — real spread, not degenerate

`Amount_to_Balance_Ratio`: mean 0.200, median 0.052, max 7.896 (i.e., at least one transaction is nearly 8× the account's balance — a strong single-feature anomaly candidate on its own). `SpendCV_Account`: median 0.541, meaning the typical account's spend variability is just over half its own mean — with 495 first-transaction accounts (and 24 single-transaction accounts, per Phase 2) contributing the `SpendCV_Account = 0` floor (no observed variability yet, by construction, documented above).

### 2.3 Cyclical time features — built, but confirmed near-zero variance on this data

`Hour_sin` has std **0.040**, `Hour_cos` std **0.200**; `DOW_sin`/`DOW_cos` each take only **5 distinct values** (std 0.461 / 0.825) because the entire dataset is confined to Monday–Friday within a 16:00–18:21 window (established in Phase 2/4). These features are retained for pipeline completeness and because a real deployment with genuine 24/7 timestamps would make them meaningful — but on *this* dataset they are near-constant and should not be expected to carry discriminative signal; velocity/gap-based features (`TimeSinceLastTxn`, `Velocity_1D/7D_Count`) are the load-bearing time-derived signals here, consistent with the Phase 4 handoff note.

### 2.4 Network-proxy features — a genuine, unexpected data-generation finding

This is the most important honest finding in this phase. `DeviceSharedAccounts_Prior > 0` for **1,830/2,512 rows (72.8%)**, `IPSharedAccounts_Prior > 0` for **1,919/2,512 (76.4%)**. Looked at dataset-wide rather than prior-only: **609/681 distinct devices (89.4%)** and **552/592 distinct IPs (93.2%)** are used by *more than one* distinct account (max 9 accounts on a single device). In a real bank, 89%+ of devices being shared across unrelated accounts would mean a mule-account epidemic — that is not a plausible real-world base rate. This strongly indicates `DeviceID`/`IP Address` were **assigned quasi-randomly during data generation** rather than tied consistently to individual customers, i.e. it is a synthetic-data artifact, the same category of finding as the `TransactionDate` export-window issue documented in Phase 2. Practical consequence: `DeviceSharedAccounts_Prior`/`IPSharedAccounts_Prior` are built and retained (the underlying leakage-safe logic is exactly what a real mule-detection feature needs), but on *this specific dataset* high values are the norm, not the exception, so they should not be over-interpreted as fraud evidence here — flagged honestly rather than presented as a working mule detector. `MerchantSharedAccounts_Prior` is, as expected, shared even more broadly (mean 12.3, max 43 — every one of the 100 merchants has multiple customers by design, since merchants are a legitimately shared resource) and is a much weaker signal by nature; it is retained for completeness but is not expected to carry fraud signal on its own, only in combination with other features.

### 2.5 Behavioral flags

`ElevatedLoginFlag`: 122/2,512 rows (4.86%) — matches the Phase 2 `LoginAttempts ≥ 2` count exactly, confirming correct construction. `ATM_Credit_InteractionFlag`: 73/2,512 rows (2.91%) — matches the Phase 4 crosstab exactly.

## 3. Reconciliation With the Teammate's Feature Set (`bank_transactions_model_3.csv`)

The teammate's file (2,512 rows × 18 columns, already scaled with `StandardScaler`, log-scale-looking distributions) builds: `account_frequency`, `device_frequency`, `ip_frequency`, `merchant_frequency` (global counts), `amount_to_balance_ratio`, `high_amount_transaction` (binary flag, threshold not recoverable post-scaling), one-hot on `TransactionType`/`Channel`/`CustomerOccupation`, and `Location_FE` (frequency encoding).

| Teammate's feature | Overlap with this pipeline | Verdict |
|---|---|---|
| `device_frequency`, `ip_frequency`, `merchant_frequency` | Conceptually identical to v1's `DeviceTxnCount`/`IPTxnCount`/`MerchantTxnCount` (global counts, same idea, different name) | **Redundant** with v1 — do not add a third copy of the same signal |
| `account_frequency` | Not present in v1 or this phase in that exact global form; closest analogue here is `CustomerTxnCountSoFar` (prior-only, leakage-safe) | **Worth adopting the concept**, but prefer this phase's leakage-safe `CustomerTxnCountSoFar` over a full-dataset `account_frequency`, which double-counts future transactions into a per-row feature |
| `amount_to_balance_ratio` | Same formula as this phase's `Amount_to_Balance_Ratio` | **Same feature, independently arrived at** — good convergent validation that this is an obviously-needed feature; keep one copy |
| `high_amount_transaction` | A binary high-amount flag; this phase instead keeps `TransactionAmount` continuous and adds `Amount_ZScore_Account`/`Amount_to_RollingMean_Ratio` for a personalized, graded version of the same idea | **Worth adopting as a cheap global-threshold flag** (e.g. above the 95th percentile) to sit alongside the personalized ratio features, not to replace them — a global flag and a personalized deviation score answer different questions and are complementary, not redundant |
| `Location_FE` | Identical concept to this phase's `Location_Freq` | **Same feature, independently arrived at** — compared quantitatively against label encoding in Phase 6 |
| One-hot `TransactionType`/`Channel`/`CustomerOccupation` | Same encoding v1 already applies (`ONEHOT_MAX_CARDINALITY` in `fe_utils.py`) | **Redundant with v1** — no action needed |
| Log1p on skewed features | Not applied in this pipeline; addressed instead via scaler choice (Phase 6) | **Alternative approach to the same problem** (right-skew), not adopted directly — Phase 6 shows `QuantileTransformer` (which log1p approximates the spirit of) reshapes the distribution in a way that risks erasing the outlier magnitude signal Phase 3 deliberately preserved; `RobustScaler` is recommended instead. Log1p is a reasonable alternative worth a documented note but is not layered on top of the recommended scaler to avoid a double-transform that's hard to reason about |

Net assessment: the teammate's feature set independently converges on `amount_to_balance_ratio` and frequency-encoded `Location` — the same two ideas this phase reached independently, which is a good cross-check. Their global frequency counts (`device_frequency`/`ip_frequency`/`merchant_frequency`) duplicate v1's existing count features and should not be added a third time. `high_amount_transaction` is the one genuinely additive idea worth folding in as a simple global flag alongside (not instead of) this phase's personalized deviation features, since a global outlier flag and a personal-baseline deviation flag catch different failure modes (a globally large transaction from a high-balance account vs. a modest-but-personally-unprecedented transaction from a low-activity account).

## 4. Handoff to Phase 6 / Phase 7

- `features_v2.csv` (48 columns) is the input to preprocessing (Phase 6) and dimensionality reduction / autoencoder (Phase 7).
- Two ID columns (`TransactionID`, `AccountID`) are retained for traceability and must be excluded from any model input — every downstream script explicitly drops them, not implicitly.
- `Location_enc` (v1 label encoding) and `Location_Freq` (this phase's frequency encoding) are both kept side-by-side specifically so Phase 6 can compare them quantitatively rather than picking one by assumption.
